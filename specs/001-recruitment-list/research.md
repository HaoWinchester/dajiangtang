# 研究记录：招聘信息列表页

## 决策 1：前端采用 Vue 构建列表页

Decision: 使用 Vue 实现招聘信息列表页，包含搜索表单、表格列表、翻页、空状态、错误状态和管理员新增入口。

Rationale: 用户已指定前端使用 Vue。该功能是典型表单 + 表格 + 分页页面，适合用 Vue 的响应式状态管理处理搜索条件、加载状态和权限展示。

Alternatives considered: 原生页面、React、服务端模板。均不采用，因为用户已指定 Vue。

## 决策 2：后端采用 Java REST 服务

Decision: 使用 Java 后端提供招聘信息列表查询接口，推荐按 Spring Boot 风格组织控制器、服务、数据访问和权限校验。

Rationale: 用户已指定后端使用 Java。REST 查询接口能清晰表达岗位、城市、页码、每页数量等查询参数，也便于 Vue 前端调用。

Alternatives considered: GraphQL、服务端渲染接口、纯前端静态数据。GraphQL 对当前列表功能偏重；纯前端静态数据无法满足真实搜索、翻页和权限。

## 决策 3：搜索规则

Decision: 岗位使用关键词模糊匹配，城市按标准城市名匹配。岗位和城市同时存在时使用 AND 关系。

Rationale: 该决策来自澄清记录。岗位模糊搜索便于查找相近岗位名称；城市标准名匹配能减少误匹配。

Alternatives considered: 岗位和城市都模糊匹配；岗位和城市都精确匹配。均已在澄清中排除。

## 决策 4：默认数据范围和排序

Decision: 默认只展示正在招聘或有效岗位，并按最新发布或最近更新优先排序。

Rationale: 该决策来自澄清记录。它能避免用户看到无效岗位，也让列表默认顺序可验收。

Alternatives considered: 展示全部岗位；按需求到岗日期排序；按需求人数排序。均已在澄清中排除。

## 决策 5：分页规则

Decision: 默认每页 10 条招聘信息，列表数据超过 10 条时展示翻页能力。

Rationale: 该决策来自澄清记录。10 条适合初版业务列表的信息密度和验收测试。

Alternatives considered: 20 条、50 条、用户可选择分页大小。均已在澄清中排除。

## 决策 6：权限边界

Decision: 招聘信息列表对管理员、普通用户、企业用户可见；新增按钮仅管理员可见；未登录访客不可访问列表页。

Rationale: 与项目宪章和规格一致。前端隐藏按钮不能替代后端权限校验；后端仍需基于当前用户角色判断是否允许进入新增流程。

Alternatives considered: 普通用户或企业用户也显示禁用新增按钮；未登录访客可访问列表页。均不采用，以减少权限误解和数据泄露风险。
