### 当前仍需修复的问题

#### 1. 岗位申请页未登录状态没有展示当前岗位信息

- 严重级别：高
- 页面：`/recruitments/rec-001/apply`
- 复现：未登录状态从首页点击 `rec-001` 的“立即申请”。
- 实际：进入申请页后只显示“岗位申请信息读取失败 / 未登录或登录态失效”，没有展示当前岗位的岗位名称、公司、城市、薪资等信息。
- 期望：未登录用户可以看到当前岗位基础信息和统一风格的登录引导；只有提交申请动作需要登录。
- 影响：用户从首页进入申请页后看不到自己正在申请哪个岗位，链路中断感很强。

#### 2. 岗位申请页未登录时没有可用的提交入口或登录引导按钮

- 严重级别：高
- 页面：`/recruitments/rec-001/apply`
- 复现：未登录状态打开申请页，寻找“提交申请”或“去登录”入口。
- 实际：页面没有可见的“提交申请”按钮，脚本也找不到可点击入口。
- 期望：页面应提供清晰的“登录后申请”按钮，跳转登录后回到当前岗位申请页；如果保留提交按钮，也应可点击并给出明确登录提示。
- 影响：申请主流程没有形成自然闭环。

#### 3. 工作经历编辑入口点击失败

- 严重级别：中
- 页面：`/personal-center/work-experience`
- 复现：个人用户新增工作经历后，点击该记录的编辑入口。
- 实际：页面能定位到疑似编辑按钮，但点击超时，无法进入稳定编辑流程。
- 期望：每条工作经历应有明确可点击的“编辑”按钮，点击后弹窗或表单必须带入原数据。
- 影响：用户保存错内容后无法修改。

#### 4. 工作经历删除入口不可用

- 严重级别：高
- 页面：`/personal-center/work-experience`
- 复现：个人用户新增工作经历后，点击删除入口。
- 实际：页面能定位到疑似删除按钮，但点击超时，记录没有被删除。
- 期望：删除按钮可点击，二次确认后删除数据库记录，页面和刷新后状态保持一致。
- 影响：用户无法维护自己的经历数据。

#### 5. 项目经历新增后的编辑流程异常

- 严重级别：高
- 页面：`/personal-center/project-experience`
- 复现：新增项目经历后，点击第一条记录的编辑入口。
- 实际：编辑入口点击超时，无法验证编辑回填和保存。
- 期望：项目经历新增、编辑、回填、保存、刷新后保留、删除都要完整可用。
- 影响：个人中心模块仍存在“能新增但不能维护”的断点。

#### 6. 人才列表“查看详情”没有跳转到具体详情页

- 严重级别：高
- 页面：`/talents`
- 复现：在人才库搜索到当前用户资料后点击“查看详情”。
- 实际：页面仍停留在 `http://127.0.0.1:5174/talents`。
- 期望：跳转到 `/talents/{id}`，并展示该人才对应的数据库详情。
- 影响：人才库列表到详情主链路不闭环。

#### 7. 控制台存在申请页接口 401 报错

- 严重级别：中
- 页面：`/recruitments/rec-013/apply`、`/recruitments/rec-001/apply`
- 实际：浏览器控制台出现 `401 Unauthorized` 资源错误。
- 期望：如果未登录访问申请页是允许的，岗位基础信息接口不应 401；如果提交申请需要登录，应只在提交动作时触发权限拦截，并展示友好提示。
- 影响：用户看到的是失败页，开发侧也不容易区分“正常登录拦截”和“页面加载失败”。

### 本轮确认通过的路径

## 第一轮历史记录（修复前）

招聘信息列表的搜索、分页、点击进入详情这条主链路当前基本可用，但系统仍有多处“页面看起来有功能，实际没有业务闭环”的问题。尤其是个人资料、申请、人才库、人才动作、数据分析等模块，存在没有后端接口、没有数据库持久化、静态数据与当前岗位不一致的问题。

## 必须修复

### 1. 岗位申请页与当前岗位不一致

- 页面：`/recruitments/rec-001/apply`
- 复现：从 `rec-001` 岗位详情进入申请页。
- 实际：申请页展示的是 `Global Tech Corp`、`数字化转型部`、`¥35k - 55k` 等静态设计稿内容。
- 期望：申请页必须读取当前岗位 ID 对应的数据库招聘信息，例如 `rec-001` 应显示“项目经理 / 北京示例科技有限公司 / 15k-25k”等真实信息。
- 风险：用户申请的岗位和页面展示岗位不一致，属于严重业务跑偏。

### 2. 岗位申请提交没有真实闭环

- 页面：`/recruitments/rec-001/apply`
- 复现：填写姓名、手机号、申请说明，勾选确认后点击“提交申请”。
- 实际：只提示“申请已提交，平台联系人会尽快跟进”，浏览器没有发出任何 `/api/` 请求。
- 期望：提交申请应写入数据库，并能被后续查询、管理、审核或至少在对应岗位/账号下查询到。
- 风险：客户部署后申请数据丢失，用户以为提交成功但系统没有记录。

### 3. 个人中心资料不是账号级持久化

- 页面：`/personal-center`
- 复现：填写个人资料并保存，同浏览器刷新后可见；换一个浏览器上下文，以同一用户角色进入后资料消失。
- 实际：保存过程没有发出 `/api/` 请求，数据疑似只保存在浏览器本地。
- 期望：个人资料必须保存到数据库，并按登录账号读取。
- 风险：换设备、清缓存、客户部署迁移后资料丢失。

### 4. 项目经历新增流程不可完整保存

- 页面：`/personal-center/project-experience`
- 复现：点击“添加项目经历”后填写数据。
- 实际：本轮探索未找到可完成提交的“保存”按钮；该流程没有形成稳定的新增闭环。
- 期望：项目经历、获得荣誉、教育经历、专业技能、资格证书等左侧模块都应支持新增、编辑、删除、保存、刷新后保留，并写入数据库。
- 风险：个人中心多个核心模块仍可能只是界面展示。

### 5. 招聘详情页详情字段仍是“待补充”

- 页面：`/recruitments/rec-001`、`/recruitments/rec-013`
- 实际：岗位说明、岗位要求、技能要求、福利待遇等显示“待补充 / 待沟通”。
- 期望：客户演示数据应完整，尤其是招聘详情页不能大面积展示占位内容。
- 风险：演示观感像半成品，也会影响申请页信息确认。

### 6. 数据分析页没有系统数据联动

- 页面：`/analytics`
- 实际：页面展示 `岗位总数 1,284`、`活跃人才 45,920` 等静态指标，加载时没有任何 `/api/` 请求。
- 期望：数据分析至少应从数据库统计招聘岗位、人才、申请、企业等核心数据。
- 风险：客户新增数据后分析页不会变化，属于假数据。

### 7. 人才库信息检索是前端静态筛选

- 页面：`/talents`
- 复现：按城市“北京”检索。
- 实际：页面筛选有变化，但没有任何 `/api/` 请求。
- 期望：人才列表、搜索、分页应从数据库读取，并支持姓名、公司、行业、城市等真实查询条件。
- 风险：人才数据无法部署维护，分页与筛选不能代表数据库真实状态。

### 8. 人才详情动作没有真实业务结果

- 页面：`/talents/sample`
- 按钮：立即沟通、下载简历、收藏此人。
- 实际：没有 `/api/` 请求，动作停留在提示/面板层面。
- 期望：立即沟通应生成联系/沟通记录，下载简历应有真实文件或明确禁用状态，收藏此人应写入账号收藏数据。
- 风险：按钮看起来可用，但客户实际操作没有结果。

### 9. 权限仍主要依赖前端角色标记

- 观察：前端大量依赖 `localStorage` / `USER_ROLE` 判断角色。
- 期望：页面展示可以做前端控制，但关键数据接口必须由后端登录态和权限校验决定。
- 风险：客户环境中用户角色边界不稳，容易出现“点着点着进入其他角色页面”的体验。

## 本轮通过的点

- 招聘信息列表支持按城市“北京”模糊搜索，并发起 `/api/recruitments` 请求。
- 招聘信息列表中点击岗位名称可以进入对应详情页。
- 企业中心“核心福利”中的 `五险一金`、`餐补/交通补助`、`年度体检` 可以点击选中/取消。

## 后续修复优先级

1. 先补岗位申请闭环：申请页读取岗位详情，提交写库，申请结果可查询。

3. 再补人才库后端：列表、搜索、分页、详情、收藏、沟通、简历下载。
